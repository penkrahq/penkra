# Production thread stall evidence — 2026-09-27

The installed production app was Penkra 0.14.0. Source observations below were checked against the 0.14.0 release commit and the 0.14.1 worktree. Times are UTC. No live SQLite file was opened.

## Distinct failure boundaries

- Provider delivery: one durable provider-intent reader processes events serially across threads. A controlled test held thread A's provider session start for 400 ms, admitted thread B's turn, and observed that B's provider start was not called until A timed out. This reproduces cross-thread delivery blocking in the current source, not the historical cause of every production stall.
- Command admission: at 05:59:27, a `thread.activity-read-model.touch` command was still in flight after its 45-second dispatch deadline. A separate `thread.update` timed out before it started at 06:00:13. Earlier, a new Claude thread's `thread.create` timed out before it started; its later turn failed because the thread did not exist. Those attempts did not reach Claude.
- Socket admission: direct unauthenticated `/ws/bootstrap` handshakes against the running production backend completed in 106, 8,802, 7,079, 5,867, 5,893, 130, 5,530, and 5,986 ms. The 0.14.0 browser retired each connection attempt after 3,000 ms. Six measured successful handshakes exceeded that deadline. Isolated Dev 2 opened the same route in 7 ms.
- The production `/health` route returned 200 but intermittently took 6–9 seconds. This demonstrates backend responsiveness can lag independently of provider turn acceptance. The exact operation delaying the backend remains unidentified.
- Strategy's Claude turn start repeatedly hit the 120-second provider deadline, including after a clean restart. The startup phase responsible for that delay remains unidentified and is separate from the new thread's pre-provider command-admission failure.

## Historical design constraints

The initial shared provider queue preserved deterministic ordering. A later drainable worker added shutdown completion semantics, and the durable event source added cursor replay, delivery claims, ambiguous-outcome fencing, and per-thread quarantine. A concurrent delivery design must retain these guarantees and preserve order within each thread. Advancing the durable cursor past an in-memory task before it is durably recoverable would lose work after a crash.

## Controlled checks

- `ProviderCommandReactor.test.ts` diagnostic cross-thread case: pass.
- `ProviderRuntimeIngestion.test.ts` controlled slow-event case: held thread A's provider-derived command, observed unrelated B's event and cursor remain blocked, then released A and observed B advance. This reproduces runtime-event cross-thread blocking in the current source; it does not identify the operation that slowed the production worker.
- `OrchestrationEngine.test.ts` controlled slow-read case: held A's thread-detail load outside a SQLite transaction, observed an unrelated folder command B wait, then released A and observed B complete. This reproduces cross-thread command-worker blocking without an external provider or shared SQLite hold; it does not identify the production command's slow stage.
- In an isolated browser transport experiment, a 17,600 ms successful two-stage open failed at the existing 3,000 ms attempt deadline and passed with a 30,000 ms deadline. The two-stage case represents bootstrap and feature WebSocket handshakes in sequence; 8,800 ms was the longest directly measured single handshake. The experimental timeout change was removed pending root-cause investigation.
- `OrchestrationEngine.test.ts`: 25 passed. Web and server typechecks passed.
- An isolated synthetic receipts query showed a full scan after the sequence index removal, but 100,000 rows took about 4 ms per cleanup. That is insufficient evidence to attribute the 45-second production command stall to this query. No persistence optimization was made from that observation.

Experimental command-stage and event-loop diagnostics were initially removed pending an observability design. A later, targeted diagnostic-only patch in this local worktree adds bounded slow-stage records after the investigation below. It is not in the installed production app.

## Follow-up, 2026-09-28 04:00–04:53 UTC

The installed 0.14.1 backend remained live without a restart. Its provider runtime journal had no sequence gap at 04:00 UTC. Intermittent gaps appeared by 04:08; a sustained gap began around 04:18. At 04:42 the gap was about 5,800; by 04:53 it was about 25,900, while the backend used roughly 86% CPU. By 05:00 the gap had fallen to about 3,150, showing partial catch-up without a restart; the oldest pending worker item was still about 200 seconds old. The journal made progress in bursts, but incoming runtime events outpaced its processing during the worsening interval.

The existing per-interval metrics recorded runtime event processing as long as 28–54 seconds, SQLite transaction holds as long as 15–19 seconds, and SQLite semaphore waits as long as 25–42 seconds. These are maxima from different operations, not a single joined trace. The sum of concurrent semaphore waits is not elapsed wall time. Slow-event logs show individual provider events committed 12–20 minutes after receipt across Codex, Claude, and OpenCode threads; most of that was pending time before processing. The installed metrics do not identify the event responsible for each long processing sample, the owner of each long SQLite transaction, or the active orchestration worker stage.

Journal sequence-rate estimates from the metric samples: 04:18–04:30 produced about 10.4 events/s and processed about 4.2/s; 04:30–04:53 produced about 25.5/s and processed about 10.9/s; 04:53–05:00 produced about 8.7/s and processed about 63.3/s. The backend could catch up when the incoming rate fell and processing accelerated. These rates describe throughput, not which operation caused the earlier low throughput.

During a direct check at 04:42 UTC, five production bootstrap WebSocket handshakes opened in 8–110 ms, and the health route returned 200 in 2–637 ms. Socket admission was responsive during this sample; the earlier measured multi-second handshakes remain intermittent. Dev 2's isolated journal reported zero gap at startup. No live SQLite file was opened, and no production behavior was changed.

At about 05:20–05:22 UTC, while the journal gap rose from 5,250 to 6,413 events, an unauthenticated read-only `/health` request connected to the backend TCP port in 10 ms but received no HTTP response before its 8-second timeout. A separate request took 5.6 seconds; neighboring requests completed in tens of milliseconds. Eight sequential read-only WebSocket opens to `/ws/bootstrap`, using a 3.5-second handshake deadline, produced three handshake timeouts and five successful opens (the successful attempts ranged from 2 ms to 1.3 seconds). Five subsequent opens all succeeded in 2–269 ms. This directly reproduces intermittent production socket admission delay, without attributing it yet to the journal, a SQLite operation, or event-loop blocking. The `/health` route only reads an in-memory readiness snapshot; it does not query SQLite.

At 05:07–05:13 UTC, the journal backlog rose from 1,165 to 1,676 events. Its oldest pending worker item aged to 490 seconds before the page finally drained and the age reset. The slow-event records show the batch contained events processed as early as 05:04:25, but its cursors did not commit until 05:12:44. Because the batch commit follows `worker.drain`, the long delay in this instance was before the batch commit, not in its cursor-update transaction. During this interval, individual SQLite semaphore waits reached 83 seconds and transaction holds repeatedly reached 8–15 seconds. Every sampled interval in that period reported zero retention scans. This rules out retention cleanup as the sole source of those transaction holds; the installed metrics still cannot name the holder or determine which operations were inside each hold. A Codex `thread.turn-start-requested` delivery also entered terminal failure after its 120-second deadline at 05:10, then its delivery blocker recovered automatically at 05:11. Recovery of that blocker did not clear the journal backlog.

The local diagnostic patch records the active command worker stage at 5 and 30 seconds, in-flight and completed runtime-event processing over five seconds, slow provider-command receipt lookup/dispatch, SQLite transactions held over five seconds with acquire/release UTC timestamps, backend event-loop delay over two seconds with its sample window, and cursor-batch wait/inside-transaction stage with its event sequence range. An isolated test held a SQLite transaction while dispatching a command and confirmed the worker record named `receipt-lookup` and the SQLite hold record appeared. This reproduces a contention path; it does not prove that path caused the production backlog. The next production occurrence must be observed with these IDs and stages before selecting a behavioral fix.

The patch also records any synchronous SQLite prepare or execute operation taking at least two seconds, with the owning fiber ID, phase, SQL-text hash, parameter count, duration, and completion time. It does not log SQL text or parameter values. The hash lets a later offline source comparison identify a repeated query without exposing values in production logs. A long transaction with no matching slow synchronous operation suggests time was spent elsewhere while the connection remained held; it does not itself identify that wait.

The transport now records `/health` handler intervals and `/ws/bootstrap` upgrade intervals only when they exceed two seconds or remain in flight at 3.5 seconds. These clocks start when Node emits the request or upgrade event. If an external probe stalls but neither interval is slow, compare the event-loop histogram for that interval: the delay occurred before the handler was entered or outside this backend. The logs alone cannot distinguish those two cases without the paired external probe.

The local provider-command diagnostic also records in-flight provider calls at five and thirty seconds, and completed calls over five seconds. Its operation identifies session start, turn send, turn steer, or review start; its fields include provider, thread, and message ID when available. It does not yet split a slow session start into child-process spawn, handshake, resume, and provider acceptance. No installed production occurrence has been captured with these new records.

At 05:56 UTC, a fresh standard Dev 3 desktop instance started after its stale launcher was reinstalled against the active shared `dev-consolidated` workspace. Its five read-only `/health` probes completed in 3–6 ms, and five bootstrap WebSocket handshakes opened in 5–37 ms. This is a quiet-instance control only: Dev 3 runs the shared source, not this diagnostic worktree, and it did not reproduce the production backlog or validate the patch in a desktop app.

For a rough instrumentation-cost check, 20,000 trivial sequential Effect operations took 9 ms without the event watchdog and 156 ms with a forked, immediately interrupted watchdog on this machine, about 7 microseconds added per event. This synthetic measurement does not include real projection or SQLite work. The full provider runtime ingestion test file passed all 150 cases after the watchdog was added, in 35.5 seconds. No production throughput claim follows from either check.
