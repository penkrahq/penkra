# Thread runtime isolation design — proposal

Status: architecture for review. No behavioral change is implemented here. The evidence is in [production thread stall evidence](./production-thread-stall-evidence-2026-09-27.md).

## What the current system proves

The provider command reactor reads the orchestration journal in global sequence order. `processOrderedEventSerially` holds one `deliverySourceLock` permit while it executes the provider intent. A controlled test held thread A's provider start and observed thread B's start waiting behind it. The global lock protects ordered cursor advancement and replay, but its critical section includes external provider calls. That is the proven provider-delivery coupling.

There are two more shared execution points. `ProviderRuntimeIngestion` uses one `makeDrainableWorker` consumer for all provider runtime events and waits for the entire fetched page to drain before it commits the page's thread cursors. The observed page that took about eight minutes did so before the cursor commit. A controlled ingestion test now holds event A in a provider-derived command and proves unrelated thread B's event and cursor remain blocked until A is released. `OrchestrationEngine` uses one command worker for all threads, with bounded priority queues. A controlled engine test holds thread A's detail load and proves an unrelated folder command B waits until A is released, without holding SQLite or calling a provider. A separate SQLite-holder test makes a command wait at receipt lookup. Production logs show commands timing out before start and while in flight, but the exact expensive production operation is still unknown. Finally, `NodeSqliteClient` gives the backend one SQLite connection guarded by a semaphore. All three execution paths can contend there.

The installed production backend also delayed an in-memory `/health` response beyond eight seconds after TCP connected, and three of eight direct WebSocket bootstrap attempts exceeded a 3.5-second handshake deadline during journal backlog. The delay's owning operation is unknown. A 120-second Claude turn-start timeout may be a provider or Penkra startup-phase failure. Neither the socket nor Claude root cause is proven by the global provider lock reproduction.

## End-to-end target

The target is independent progress for unrelated provider sessions, with explicit and bounded contention at shared storage. Intake and publication should not await external provider calls, slow projections, or a subscriber. Work that must remain ordered within one session or thread stays ordered there. A slow or uncertain session is contained to its lane. A saturated SQLite writer is surfaced as a measurable capacity failure rather than disguised as a socket-open or provider timeout. Network admission remains responsive while the engine is busy, and the UI distinguishes connected, queued, running, blocked, and uncertain states.

This is an architectural target, not a claim that the installed production failures all have one cause. It requires changes at provider delivery, runtime projection, command execution/publication, and the network/storage boundary. Fixing only one of those shared points will leave the others able to reproduce the same user-visible stall.

## Delivery contract

Move provider calls out of the global journal reader. The preferred steady-state boundary is a **transactional outbox**: when `OrchestrationEngine` appends a provider-intent event, it also inserts that intent's delivery job in the same SQLite transaction as the event and command receipt. The global delivery reader disappears after migration; it no longer performs provider calls or serves as the safety boundary. A job has a stable idempotency key, lane identity, source sequence, state, owner generation, attempt count, and outcome classification. It either stores the complete required intent payload or pins the source journal event against retention until settlement; a sequence reference alone is insufficient because the current global cursor allows acknowledged journal history to be collected.

One worker executes jobs in order within each provider-session lane. Unrelated sessions may run concurrently under a bounded global active-lane limit. A child thread sharing a parent provider session uses the same lane. Lane identity must be derived from the authoritative session binding and generation at assignment, then retained with the job; a later binding change must fence or migrate unfinished jobs explicitly. Thread-local operations that do not touch that session still require a documented ordering relationship with that session's jobs. A lane's completion is recorded in its own durable job state; it does **not** rejoin the global reader or wait for earlier work in another lane.

For example, if Claude session A takes 120 seconds to start and an unrelated Codex session B receives a turn afterward, both command commits leave durable outbox jobs. A remains busy in its lane; B starts when a bounded worker slot is available. A later command for A waits behind A. A child using A's provider session also waits behind A, by design.

## Safety and recovery invariants

1. **No gap:** The orchestration event, provider job, and command receipt commit atomically. A crash cannot leave an acknowledged event without a job or a job without its event. Legacy events pending at cutover are assigned idempotently before the old reader is retired.
2. **No missing source:** Retention cannot delete an event still needed by an unfinished lane job. A job that stores its own payload is self-contained; a referencing job keeps the source row pinned through terminal settlement.
3. **One session owner:** At most one normal provider command owns a provider-session lane at a time. A claim has an owner generation/lease; a stale worker cannot settle a newer generation.
4. **No blind replay:** If a provider call may have been accepted but no acknowledgement was recorded, its job becomes `uncertain`. The existing runtime-stop fence must prove the old session cannot execute before the ambiguous command is abandoned or any later side effect is released. Replay-safe and provably rejected commands may retry; acceptance-ambiguous turns do not.
5. **Stop remains an escape hatch:** Stop/interrupt cannot sit forever behind a stuck start in the same ordinary lane. A supervised control path cancels or fences the lane owner, stops the session generation, settles the affected turn, and only then releases later work. This path requires a race test against provider acceptance and late terminal events.
6. **Backpressure is explicit:** Memory holds only bounded active work. Pending jobs remain durable. When storage or queue limits are reached, admission reports an actionable failure instead of silently dropping or accepting work that cannot progress.
7. **Shutdown drains or resumes:** On shutdown, claims settle or remain recoverable. Startup rebuilds lane ownership from durable jobs and existing delivery/blocker state. Migration from the old global cursor must preserve previously accepted, uncertain, and quarantined outcomes. The cutover cannot run old and new executors against the same intent; it must fence the old owner before enabling the new one.

The existing `orchestration_event_deliveries` claim states cover only selected intents; some provider intents currently advance the cursor without a claim. The outbox must include every provider intent or prove it is a no-op. A migration must reconcile old delivery states and blockers before backfilling unfinished source events. Merely forking the current `processOrderedEvent` and advancing the global cursor would lose or duplicate work after a crash.

## Runtime events and command execution

The runtime-event journal already has per-thread cursors and a failure ledger, but one worker still processes every event. Existing tests show that a failed, quarantined event in A can be skipped so B later progresses; the new controlled test shows B does **not** progress while A's event is merely slow and still in flight. A bounded scheduler should execute events in order within the owning provider session or thread while allowing unrelated lanes to progress. Each lane commits its own cursor after its events become durable, rather than waiting for every worker in a global page. The scheduler must not share the current mutable page buffer across concurrent lanes. Quarantine and retry stay scoped to the lane; a corrupt or slow event in A cannot hold B's cursor. Events from child threads sharing one provider session need an explicit ordering rule before parallelism is introduced.

The orchestration command worker must also cease doing long work under a global serialized worker. A candidate shape is parallel preparation and per-aggregate decision making, followed by a short serialized commit that checks the versions read by the decision, writes the durable events and receipt, and retries a genuine version conflict. Commands touching shared folder/deck state or multiple threads need a stable lock order or one explicitly shared aggregate lane. Global event sequence remains assigned at commit. Publication should be driven from the durable event log so a slow subscriber cannot hold the command worker's uninterruptible publish step. This changes core invariants and needs an independent failing reproduction and review before implementation.

SQLite still has one writer. The design must measure and bound transaction duration, avoid provider/network waits while holding the connection, and identify any production query that holds it for seconds. Parallel lanes cannot make a single saturated writer process more writes than it can sustain. If measured write demand exceeds capacity, admission/backpressure and data-model changes are required; adding workers alone would amplify contention.

## Backend responsiveness boundary

The lane design prevents provider A from holding provider B's delivery reader. Per-lane runtime projection and shorter command commits address the other shared queues. None of those alone guarantees that a WebSocket opens while the backend event loop is blocked. The production health probe shows a delay before the server returned an in-memory response, but the installed logs do not identify the blocker.

The narrow fix depends on the owner trace: optimize or bound an identified synchronous query/projector if one operation is responsible. For a stronger isolation guarantee, keep HTTP/WebSocket admission on a small event loop separate from synchronous SQLite and CPU-heavy projection work; a dedicated database worker or engine process would own those operations and communicate asynchronously. The front door can then open a socket and report engine readiness even when the engine is slow. It must not claim a message was accepted until the durable command receipt exists. This split adds IPC, supervision, shutdown, and crash-recovery complexity, so it should be justified by measured production stalls, not assumed from the socket timeout alone. Extending the browser's three-second deadline only changes how long the user waits and is not a root fix.

## Provider startup boundary

Each lane should record separate phases for session creation, provider request dispatch, provider acceptance, first runtime event, and terminal settlement. A deadline identifies which phase failed. If startup failed before dispatch, a fresh session can retry safely. If acceptance is ambiguous, fence the old runtime before any retry or mark the turn uncertain and surface the state. An external provider can still fail or stall; the system can guarantee containment and honest recovery, not that Claude will return. The observed Strategy/Claude timeout needs its phase identified before selecting a Claude-specific change.

## Alternatives and acceptance criteria

- **Fork after reading, advance the cursor immediately:** simple, but loses in-memory work on crash and breaks delivery ordering/replay. Reject.
- **Keep one global reader and shorten provider timeout:** caps the outage duration but every other session still waits behind the slow call. Reject as the final design.
- **Per-thread workers without durable assignment:** isolates live sessions but restart can skip or repeat commands. Reject.
- **Durable session lanes with bounded workers:** preferred for the proven cross-thread delivery defect. The same ordered-lane principle must cover runtime projection; the command worker needs its own short-commit design. Provider lanes alone are incomplete.
- **Separate network front door:** strongest socket-admission isolation, but only warranted after the new timing records identify a server-side blocking class that cannot be removed reliably in the current process.

The controlled A/B test must fail on the old global reader and pass on the lane design while A remains hung. A second A/B test must stall A's runtime-event projection and prove B's event and cursor advance. A third must hold A's command and prove B's command can complete without violating shared-aggregate order. Crash tests must cover every transaction boundary from event append through lane settlement, including an ambiguous provider acknowledgement. Tests must cover parent/child shared sessions, queued turns, stop during startup, late terminal events, recovery of old blockers, bounded capacity, and idle shutdown. For the socket symptom, reproduce a delayed bootstrap and `/health` response in a fresh numbered Dev instance under the measured blocking condition; verify the fix against the same condition, not only a quiet server. Claude changes require a captured phase and a matching fresh/restored-thread reproduction.
